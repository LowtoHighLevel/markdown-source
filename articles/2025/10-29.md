## Architecture Flaws
There are two main gripes with the current architecture that I have at the moment. The main one is that I have no easy way to reset / handle input for a device. The only way that I could think of, is to have memory poll for interrupts, which I think will be a hassle later on. What I'm looking into more now, is to have a vector table stored in RAM, with a pointer to it at the first location in physical RAM. I think that will be a little more beneficial in the long run.

The vector table as of right now, will probably only need two vectors at the moment, so it should look like this:

| Name | Address | Size |
| - | - | - |
| Reset | 0x0 | u32 |
| Interrupt | 0x4 | u32 |

The reset vector will be the address that code will start from when the system is reset, and the interrupt vector will be the location that we jump to as soon as an interrupt is called. Theoretically we may be able to do this in hardware, or software (with software needing a new instruction)

So, instead of digging deep into the GNU system and toolchain, I think I will dig deeper into this feature first, and put it into our emulator.

We can test it later by either writing some C or java code that generates some source code, or we can use a temporary assembler that I wrote. This is a program that is **very** bare-bones, which is designed to help me get my feet off the ground when testing the machine. It is not a complete assembler, and is missing a ton of core features, but it can help us when we want to get things to work.

It's definitely an idea to consider, but I definitely will implement the table feature, as it will help us a lot in the future, especially when it comes to start writing a BIOS or bootloader.
