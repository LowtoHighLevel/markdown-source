### CPU
The main functions that the main program calls, are in the CPU.

Let's take a quick look at the header file for the CPU.

Here we have a couple of preprocessor definitions, that are used in the CPU emulation.

We also have an enum that determines our types of instructions.

We also define two public functions, init, and run_cmd.

init will initialize the CPU and run_cmd will run a single instruction.

our init function sets all of the CPU's flags to 0, clears all registers, and sets our instruction pointer to a starting vector.

That is a new feature since the last time you saw this. Basically our start vector is the last four bytes in memory. That will determine where our computer will go when it first starts.

With the way that we have been running our CPU, and the way that it has currently been set up, this value will always be 0.

Ideally, I would want to move our ROM to the end of memory in the future where we can redefine this, but that will be a problem for the future.

Let's look at how we run an instruction.

First we read an instruction from memory at the instruction pointer.

Next, we parse that instruction. This splits our opcode into different tools for our emulator to handle later.

First we get the instruction type from the first three bits, then we do a switch on the types.

Depending on the instruction type, our data is handled differently.

For example, a register type will set the control bits as the 5 bits immediately after the type.

The next sets of 8 bits are the register numbers, with an immediate value of 0, as it is unused in that type of operation.

We do something similar for every other type of CPU type.

After we parse an operation, we will read the data for registers 1 and 2. This will be our ALU's A and B values.

If it is zero, then we will load register 0 which always has a value of zero.

Next, we get a relative address from the command. This is only used for a relative jump.

from there, we gather a check value.

This compares the 5-bit control value.

If the control value is zero, then it's absolute.

For the other cases, it depends on the values of the flags. The value is based on the flag number. Previously this was a series of OR gates based on variables, but I since changed it to a single 32 bit integer, which is gathered based on its needs.

The flag number starts at zero, but our condition numbers are offset by one, because of the absolute condition. This is why our conditions are offset by 1.

After we check our conditions, we will check the type of instruction.

If it's a jump relative, and the conditions are met, we will do a relative jump.

For register jumps, we will check our condition, then jump based on the value of the regsiter.

For a register type instruction, we will run the ALU, and output to our output register.

For immediates, it's similar, we will run an alu operation, and then write the immediate value to our output register

Memory reads will do an alu operation, and then read from memory into our output register

Memory writes will do something similar, but then it will write to the address of data 1 the value in data 2.

Any other instructions are unhandled.

### ALU
Let's take a quick look at the ALU.

In our header, we have different operations that the ALU can perform.

Those are Adding, boolean logic AND, OR, XOR, and some rotate functions.

When we run an alu operation, we will pull out our carry in and whether to invert B from the control.

Invert B will do a Bitwise NOT on the B register.

carry_in will set the carry in of the ALU to 0 or 1 when we use it for adding.

The rest of the control bits are the ALU operation.

for a rotate right, we will shift all the bits to the right, with te rightmost initial bit going into the carry flag, and the carry bit going into the leftmost bit.

Rotate left is similar, instead we shift to the left, with the carry bit going in to the lowest bit and the highest bit going into a carry.

For any other operations, we will iterate through the bits, setting the inverse of b when needed, and then doing an individual operation on the rest of the ALU.

If we are adding, then we do an addition on the bit of carry_in + a + b,

a bitwise and will do A & B

or will do A | B

and an XOR will do a bitwise XOR on A and B.

Our add function is a little special, as it would in real life require more logic gates.

Looking back at Episode 2, we created a half adder. This emulates one exactly the same as we had then.

We use the half adders to create a full adder, just like episode 3. This is exactly how we did it before, just in C code instead of pure logic gates.

After we use the ALU, we will write it to our output, then update the carry bit for the next bit.

Once all of that is done, we will update the overflow and carry flags on the CPU.

From there, we will check if it is negative, and then update that flag.

Then we are done with an alu operation.

We have a couple of extra methods here as well.

### Util
Our util file helps convert integer values into arrays of just their bits for the ALU.

It also has a method for logging to output to help with debugging.

### registers

Our registers file stores our emulator's registers and flags.

It has a couple of helper functions.

Most of them involve reading and writing to the registers, getting the instruction pointer, and getting either all or a specific flag.

### memory
Our memory files handles the emulator's memory

By default, we have 4 kilobytes of ROM stored at address 0. Immediately following that is 8 kilobytes of RAM.

We also have a single byte of memory mapped i/o at address 16384.

Calling a memory write at this address will run a printf on the least significant bit in the value register.

The rest will attempt to go to other places in memory, though they don't exist, so it is ignored.

We also have a couple of functions to write to the ROM, though this should not happen while the CPU is initialized and running. It is purely for the emulator to set things up.
